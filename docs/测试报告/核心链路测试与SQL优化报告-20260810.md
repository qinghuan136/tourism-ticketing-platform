# 核心链路测试与 SQL 优化报告

## 1. 测试目标

本轮测试不追求覆盖所有接口，而是从项目中选择四组更适合面试说明、且复杂度适中的场景：

1. 订单一人一单并发正确性；
2. 景点详情两级缓存性能与多实例失效；

4. 运营趋势统计 SQL 的执行计划分析与索引优化。

重点不只是接口是否返回成功，还要验证库存守恒、唯一性、最终一致性、数据库回源次数和执行计划变化。

## 4. 测试一：订单一人一单并发正确性

### 4.1 为什么选择这个场景

该场景同时经过以下核心逻辑：

- JWT 游客身份；
- 以“场次 + 参观人”为粒度的 Redisson 锁；
- 事务内查询已有有效订单；
- 创建订单和订单明细；
- 条件扣减场次容量与场次票种库存。

相比只测 Service Mock，它更能证明 HTTP、Redis 锁和 MySQL 事务组合后的实际效果。

### 4.2 准备步骤

在正式业务库中临时创建了带有明确测试标记的数据：

- 1 个未来场次，容量 20；
- 1 个场次票种，分配数量 20；
- 账号 `jmeter_tourist_001` 下的 1 个测试参观人。

测试结束后，这些数据及测试产生的订单均已删除。

### 4.3 执行方法

1. 使用测试游客账号登录，取得 JWT；
2. 启动 30 个 PowerShell 后台任务；
3. 所有任务等待同一个开始时间；
4. 同时请求 `POST /tourist/orders`；
5. 请求体中的场次、参观人、场次票种完全相同；
6. 查询订单、订单明细和两级库存进行核对。

### 4.4 结果

| 指标 | 结果 |
|---|---:|
| 并发请求 | 30 |
| HTTP 201 | 1 |
| HTTP 409 | 29 |
| HTTP 500 | 0 |
| 平均响应时间 | 321.53ms |
| P95 | 398ms |
| 最大响应时间 | 468ms |
| 有效订单 | 1 |
| 订单明细 | 1 |
| 场次剩余容量 | 20 → 19 |
| 票种剩余数量 | 20 → 19 |

### 4.5 结论

同一参观人的 30 次并发请求只有一笔成功。其余请求均为可预期的业务冲突，而不是服务异常；场次和票种库存都只扣减一次。

这说明当前实现中，Redisson 锁负责把同一业务键的操作串行化，事务内冲突查询负责判断是否已有订单，MySQL 库存条件更新负责最终库存正确性。

## 5. 测试二：景点详情两级缓存

### 5.1 场景 A：冷缓存与热缓存性能

#### 测试步骤

1. 精确删除 Redis 中的 `venue:detail:1`；
2. 启动一个 Caffeine 为空的新应用实例；
3. 第一次请求 `GET /public/venues/1`，使其回源 MySQL；
4. 使用同一 HTTP 连接连续请求 500 次；
5. 统计冷请求和热请求耗时；
6. 查看 MySQL `performance_schema.events_statements_summary_by_digest` 中对应景点查询的累计次数。

#### 测试结果

| 指标 | 结果 |
|---|---:|
| 冷请求状态 | HTTP 200 |
| 冷请求耗时 | 483ms |
| 热请求数量 | 500 |
| 热请求平均耗时 | 2.342ms |
| 热请求 P95 | 5ms |
| 热请求最大耗时 | 26ms |
| 景点详情 SQL 的 `COUNT_STAR` | 2 |

`performance_schema` 的 Digest 是 MySQL 启动以来的累计值，本轮没有清空全局统计，因此 `COUNT_STAR=2` 不应解释成严格的单轮 SQL 次数。不过，500 次热请求后该值仍只有 2，能够说明热请求没有逐次回源数据库。

冷请求包含首次类路径、连接和缓存填充等一次性开销，不应简单理解为 MySQL 单条 SQL 需要 483ms。真正有意义的是同一环境下热缓存请求稳定在毫秒级。

### 5.2 场景 B：两个实例的本地缓存广播失效

#### 测试步骤

1. 启动 8080、8081 两个应用实例；
2. 两个实例分别查询景点 1，使两边 Caffeine 都持有旧值；
3. 给数据库中的景点简介追加测试标记；
4. 删除 Redis 景点详情 Key；
5. 向 `tourism:cache:invalidate` 发布以下消息：

```json
{"cacheName":"VENUE_DETAIL","id":1}
```

6. 轮询两个实例，记录读到新值的时间；
7. 恢复数据库原值，并再次清理缓存。

#### 测试结果

| 指标 | 结果 |
|---|---:|
| Redis 接收到的订阅者数量 | 2 |
| 8080 读到新值 | 62ms |
| 8081 读到新值 | 98ms |
| 两个实例是否最终一致 | 是 |

这证明项目中的 Redis Pub/Sub 订阅者能够同时清理两个 JVM 内的 Caffeine 缓存。

### 5.3 Canal 完整链路检查

随后又执行了一次“直接修改 MySQL，等待 Canal 自动删除 Redis 并发布消息”的完整测试。15 秒内两个实例均未读到新值。

诊断结果：

- 应用日志显示 Canal Client 已连接到 `destination=example`；
- MySQL `log_bin=ON`；
- `binlog_format=ROW`；
- 但 `SHOW FULL PROCESSLIST` 中没有 Canal 对 MySQL 的 Binlog Dump 连接。

因此，本轮能够确认应用侧的“删 Redis + Pub/Sub + 清 Caffeine”逻辑正常，但当前运行的 Canal Server 没有真正消费该 MySQL 的 Binlog。后续应检查 Canal Server 的 `instance.properties`：

1. `canal.instance.master.address` 是否指向当前 MySQL；
2. 复制账号和密码是否正确；
3. 账号是否具有复制权限；
4. `canal.instance.filter.regex` 是否包含当前数据库及四张缓存相关表；
5. Canal Server 日志中是否存在连接、GTID 或位点错误。

## 6. 测试三：优惠券 Kafka 异步落库

### 6.1 初次执行发现的问题

本轮创建了一个库存为 100 的新活动，并同时启动 8080、8081 两个实例。数据库很快变为 `cache_ready=1`，但 Redis 中的活动 `enabled`、`stock` 和 `meta` 均不存在，100 次抢券全部返回 HTTP 409：

```text
优惠券活动尚未准备完成
```

这是一种比较典型的现象：数据库状态显示“已经预热”，但真正承接秒杀流量的 Redis 数据却不存在。只查看 MySQL 很容易误以为预热已经成功。

### 6.2 原预热流程与失败清理的设计意图

为了避免 Lua 在预热过程中读到一半的数据，原来的预热顺序是：

1. 将 Redis `enabled` 写成 0，暂时关闭活动入口；
2. 写入活动元数据 `meta`；
3. 写入 Redis 入口库存 `stock`；
4. 使用条件更新将 MySQL `cache_ready` 从 0 改成 1；
5. 最后将 Redis `enabled` 写成 1，正式开放抢券入口。

其中数据库条件更新近似如下：

```sql
UPDATE coupon_activity
SET cache_ready = 1,
    preheated_at = ?
WHERE id = ?
  AND status = 'PUBLISHED'
  AND cache_ready = 0
  AND claim_end_at > ?;
```

如果更新行数为 0，旧代码会认为当前活动已经不允许完成预热：

```java
if (updated == 0) {
    disableActivityCache(activityId);
    return false;
}
```

`disableActivityCache` 会删除该活动的以下 Redis 数据：

```text
coupon:activity:{id}:meta
coupon:activity:{id}:stock
coupon:activity:{id}:enabled
coupon:activity:{id}:claimed-users
```

这个失败清理机制本身有合理目的。例如活动在预热期间被运营者取消或结束时，条件更新应该返回 0，此时必须删除刚写入的 Redis 数据，防止一个无效活动继续开放。

真正的问题是：条件更新返回 0 不只代表“活动已经失效”，还可能代表“另一个实例已经预热成功”。旧代码把这两种完全不同的结果合并处理了。

### 6.3 完整竞争时间线

假设有实例 A 和实例 B，两个实例都执行自动预热任务：

| 时间 | 实例 A | 实例 B | MySQL / Redis 状态 |
|---|---|---|---|
| T1 | 查询待预热活动 | 查询待预热活动 | 两边都读到 `cache_ready=0` |
| T2 | 获得活动分布式锁 | 已经持有 T1 读取的旧活动对象 | Redis 尚无活动数据 |
| T3 | 写 `enabled=0`、`stock` 和 `meta` | 尚未执行 `tryLock` | Redis 数据正在准备 |
| T4 | 条件更新成功 |  | MySQL `cache_ready=1` |
| T5 | 写 `enabled=1` 并释放锁 |  | A 已经完整预热成功 |
| T6 |  | 使用旧活动对象执行 `tryLock`，此时成功获得锁 | B 仍认为活动需要预热 |
| T7 |  | 再次写 `enabled=0`、`stock` 和 `meta` | 秒杀入口被 B 暂时关闭 |
| T8 |  | 再次执行 `cache_ready=0 → 1` 条件更新 | 因 A 已改成 1，更新行数为 0 |
| T9 |  | 将更新数为 0 当成预热失败，调用清理 | B 删除了 A 已写好的 Redis 数据 |

最终状态是：

```text
MySQL：cache_ready = 1
Redis：enabled、stock、meta 均不存在
接口：返回“优惠券活动尚未准备完成”
```

这也解释了为什么测试中 100 次请求全部是 HTTP 409，而不是部分成功、部分失败：预热竞争发生在压测开始之前，活动入口已经整体失效。

### 6.4 为什么已经用了分布式锁仍然出错

分布式锁只保证两个实例不会在同一时刻执行临界区，并不能自动刷新进入临界区之前读到的数据。

原流程实际上是：

```text
查询待预热活动 → 尝试获得锁 → 使用查询结果执行预热
```

实例 B 在获得锁之前就已经读取了 `cache_ready=0`。虽然 B 最终是在 A 之后串行执行，但它仍然使用旧快照，因此发生的是“基于旧状态的重复串行操作”，而不是两个实例同时修改 Redis。

如果 B 调用 `tryLock()` 时 A 仍然持有锁，B 会立即返回并跳过，本次不会触发问题。真正危险的时间窗口是：

```text
B 已经查询到旧数据
        ↓
A 完成预热并释放锁
        ↓
B 才执行 tryLock，并成功获得锁
```

因此该问题具有偶发性，单实例测试通常不会出现，双实例启动且定时任务时间接近时更容易复现。

从并发模型看，这是一个“检查时刻与使用时刻分离”的问题：检查活动是否需要预热发生在锁外，真正使用这个判断发生在锁内，两者之间状态已经可能被其他实例修改。

可以用一句话概括：

> 锁阻止了同时执行，却没有阻止后来的实例拿着旧数据再次执行。

### 6.5 根因总结

本次问题由三个条件共同形成：

1. 待预热活动列表在获得分布式锁之前查询，活动对象可能过期；
2. `markActivityCacheReady` 返回 0 同时包含“活动失效”和“其他实例已成功”两种语义；
3. 更新失败分支会清理共享 Redis Key，因此后执行的实例能够删除前一个实例的成功结果。

单独看每一段逻辑都容易觉得合理：先批量查活动、用锁防止并发、条件更新防止状态覆盖、失败时删除半成品缓存。但组合到多实例时，旧快照和共享清理发生了冲突。

### 6.6 最小修复及其正确性

修复没有改动整个预热流程，只在成功获得活动锁之后重新读取一次活动：

```java
CouponActivity latestActivity =
        couponMapper.findActivityForClaim(activity.getId());

if (latestActivity == null
        || Boolean.TRUE.equals(latestActivity.getCacheReady())) {
    return false;
}

return writeActivityCache(latestActivity);
```

修复后的实例 B 在 T6 获得锁后，会重新读取到 `cache_ready=true`，于是直接返回，不再覆盖 Redis，也不会进入失败清理分支。

这里可以把两层措施分别理解为：

- 分布式锁：保证同一活动的预热过程串行执行；
- 锁内二次查询：保证当前实例基于最新数据库状态决定是否执行。

失败清理机制仍然保留，因为真正的失败仍然需要处理：

- 如果二次查询后活动又被取消，后续条件更新返回 0，删除本实例写入的 Redis 半成品是正确的；
- 如果数据库已经标记成功，但最后写 `enabled=1` 时 Redis 异常，代码仍会删除不完整缓存，并把 `cache_ready` 重置为 0，允许下一轮重新预热。

因此本次修复不是简单删除失败清理，而是避免把“别人已经成功”误判为“当前活动预热失败”。

同时增加了单元测试，模拟以下情况：预热任务持有的是 `cache_ready=false` 的旧对象，但获得锁后查询到的最新活动已经是 `cache_ready=true`。测试验证此时不执行 Redis 写入，也不再次更新数据库。

### 6.7 面试讲述参考

面试时可以按照“现象—定位—根因—修复—验证”讲述：

> 我在双实例优惠券秒杀测试中发现，MySQL 的 `cache_ready` 已经是 1，但 Redis 活动缓存全部不存在，导致所有抢券请求返回活动未准备。继续复现后发现，两个实例会在加锁前同时查到未预热活动。A 先拿锁并成功预热，B 随后拿到锁时仍使用旧对象，再次执行条件更新得到 0。旧代码把更新数为 0 一律当成预热失败，并删除共享 Redis Key，于是 B 把 A 的成功结果删掉了。分布式锁只能保证串行执行，不能保证锁前读取的数据仍然有效。最后我在获得活动锁后增加二次查询，发现活动已被其他实例预热就直接跳过，同时保留真正失败时的缓存清理和标记回退。修复后重新进行双实例预热和 100 人抢券测试，实现 100% 最终落库、零超卖和零重复发券。

如果面试官继续追问“为什么不直接删除失败清理”，可以回答：

> 因为活动可能在预热期间被取消，或者 Redis 最后启用入口时发生异常，这些情况下必须删除半成品缓存。问题不在清理动作，而在没有区分更新数为 0 的具体原因。

如果继续追问“为什么锁没有解决”，可以回答：

> 两次预热没有同时执行，但 B 使用的是锁外读取的旧快照。锁解决执行互斥，锁内二次检查解决状态新鲜度，两者作用不同。

## 7. 测试四：运营趋势统计 SQL 优化教程

### 7.1 第一步：先确定业务查询，不要先猜索引

本轮选择 `StatisticsMapper.listTrend`，因为它是典型的运营统计查询：

```sql
SELECT CAST(bo.paid_at AS DATE) AS statistic_date,
       COUNT(*) AS paid_order_count,
       COALESCE(SUM(bo.total_amount), 0) AS gross_revenue,
       COALESCE(SUM(bo.quantity), 0) AS sold_ticket_count
FROM booking_order bo
JOIN admission_session s ON s.id = bo.session_id
WHERE s.venue_id = 1
  AND bo.paid_at >= '2026-07-01 00:00:00'
  AND bo.paid_at <  '2026-08-01 00:00:00'
GROUP BY CAST(bo.paid_at AS DATE)
ORDER BY statistic_date;
```

分析索引前先明确查询过程：

1. 使用 `venue_id` 找到该景点的场次；
2. 使用 `session_id` 关联订单；
3. 过滤支付时间；
4. 读取 `total_amount` 和 `quantity`；
5. 按支付日期聚合。

### 7.2 第二步：准备有区分度的数据量

现有开发库只有少量订单，任何 SQL 都可能在 1ms 左右完成，无法体现索引差异。因此创建了独立数据库 `tourism_sql_perf_20260810`，只复制必要表结构，并生成：

- 10 个景点；
- 1000 个场次，每个景点 100 个；
- 300000 笔订单；
- 支付时间分布在约两年内；
- 查询其中一个景点的一个月数据。

测试完成后已删除整个独立性能库，没有向正式业务表灌入大批量数据。

### 7.3 第三步：使用 `EXPLAIN ANALYZE`，同时看估算和实测

普通 `EXPLAIN` 主要展示优化器估算，而 `EXPLAIN ANALYZE` 会真正执行查询，并给出实际时间、行数和循环次数。

重点关注：

- 使用了哪个索引；
- `actual rows`：每次循环实际读取多少行；
- `loops`：该步骤执行了多少次；
- `actual time`：该节点实际耗时；
- 是否出现临时表和排序；
- 读取很多行后是否只留下很少结果。

基线计划的关键部分：

```text
Index lookup on bo using idx_booking_order_session_status
actual rows=300 loops=100

Filter paid_at
actual rows=12.7 loops=100
```

含义是：

- 先找到该景点的 100 个场次；
- 每个场次平均读取约 300 笔订单；
- 共读取约 30000 笔订单；
- 时间过滤后只保留约 1271 笔。

真正的主要成本是大量订单主表数据页读取，而不是最后仅有 31 行的日期排序。

### 7.4 第四步：第一次索引尝试为什么没有效果

最直觉的索引是：

```sql
CREATE INDEX idx_booking_order_session_paid_at
    ON booking_order(session_id, paid_at);
```

但执行计划仍然选择原有的：

```text
idx_booking_order_session_status(session_id, status)
```

说明 MySQL 认为新索引成本没有明显更低。本轮数据中，嵌套循环先按 `session_id` 关联，优化器没有进一步把 `paid_at` 表现成理想的范围扫描。

这一步非常重要：索引设计不能以“文件已经创建成功”为结束，必须再次查看执行计划。没有被选择的索引只会增加写入和磁盘成本。

### 7.5 第五步：根据查询列设计覆盖索引

该统计最终还需要读取：

- `paid_at`；
- `total_amount`；
- `quantity`。

因此改成覆盖索引：

```sql
CREATE INDEX idx_booking_order_session_paid_cover
    ON booking_order(session_id, paid_at, total_amount, quantity);
```

优化后的计划变为：

```text
Covering index lookup on bo
using idx_booking_order_session_paid_cover
```

“Covering”表示查询需要的订单字段都能从二级索引叶子节点取得，不需要对约 30000 条索引记录逐条回到订单主表读取完整行。

### 7.6 第六步：重复测试并使用中位数

为减少首次磁盘读取和缓冲池预热影响，分别连续执行三次 `EXPLAIN ANALYZE`。

| 轮次 | 优化前 | 覆盖索引后 |
|---|---:|---:|
| 1 | 67.0ms | 17.2ms |
| 2 | 87.7ms | 9.68ms |
| 3 | 90.0ms | 10.6ms |
| 中位数 | 87.7ms | 10.6ms |

按中位数计算：

```text
(87.7 - 10.6) / 87.7 ≈ 87.9%
```

所以本轮测试中，运营趋势统计耗时降低约 87.9%。

### 7.7 第七步：评估索引代价

覆盖索引不是免费的：

- 订单支付时设置 `paid_at` 会维护该索引；
- 每次订单写入或相关字段更新会增加少量写放大；
- 索引额外占用磁盘和缓冲池空间；
- `total_amount`、`quantity` 放入索引会增加索引宽度。

本项目运营统计是稳定存在的读取场景，且订单支付后统计字段基本不再频繁变化，因此该取舍可以接受。索引已通过新的 Flyway 迁移落地，并在本地 MySQL 启动时成功执行：

```text
V6__add_booking_statistics_index.sql
```

### 7.8 可复用的 SQL 优化流程

以后优化其他 SQL 时，可以按以下顺序：

1. 明确接口和业务过滤条件；
2. 准备足够且有区分度的数据；
3. 记录未优化的响应时间；
4. 使用 `EXPLAIN ANALYZE` 找到读取行数最多或耗时最高的节点；
5. 根据 `WHERE`、`JOIN`、`ORDER BY` 设计候选索引；
6. 重新执行计划，确认索引真的被选择；
7. 连续执行多次，比较中位数和 P95，而不是只挑最好的一次；
8. 检查索引对写入、磁盘和其他查询的影响；
9. 通过新的 Flyway 迁移落地，不直接修改已经执行的旧迁移。
