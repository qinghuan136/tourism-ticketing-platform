# 优惠券核心链路开发前置说明（临时阅读稿）

> 用途：帮助你在完成自动预热后，继续实现 Lua、Kafka 和消费幂等，并快速理解项目中现有的优惠券背景与代码边界。核心链路完成后可删除本文件；正式业务约定仍以 `docs/database-design/优惠券秒杀业务与表设计.md` 和接口文档为准。

## 1. 目前要解决的业务问题

景点运营者可以为自己负责的景点创建一个“固定金额满减券”活动，例如“满 100 元减 20 元”，游客在指定时间内参与秒杀领取，领取成功后可以在该景点下单时使用。

MVP 只支持：

- 固定金额满减券，不支持折扣券、兑换码、券叠加和指定票种券。
- 一个活动只属于一个景点。
- 一个游客账号在同一活动中最多领取一张券，与参观人无关。
- 一笔订单最多使用一张券。
- 取消活动只停止后续领取，不作废已经发放的券。
- Kafka 只用于异步发券；订单锁券、支付核销、取消释放和退款返还仍使用 MySQL 本地事务同步完成。

这里实际存在三类不同的“库存/凭证”：

1. Redis 入口库存：承担高并发请求的快速预扣，主要作用是削峰和防止大量请求进入 Kafka。
2. `coupon_activity.remaining_stock`：数据库最终库存，消费者仍必须条件扣减，不能完全相信 Redis。
3. `user_coupon`：真正发给游客、能够在订单中使用的优惠券凭证。

因此，Lua 执行成功只表示“抢券请求取得了一个异步处理资格”，不等于数据库已经发券成功。

## 4. 数据库迁移和表关系

迁移文件：

```text
tourism-server/src/main/resources/db/migration/V4__add_coupon_feature.sql
```

表关系概览：

```text
venue
└── 1:N coupon_activity
         ├── 1:N coupon_claim_request
         └── 1:N user_coupon

user_account（游客）
├── 1:N coupon_claim_request
└── 1:N user_coupon

user_coupon
└── 1:N booking_order（历史订单可保留同一张券的引用）
```

### 4.1 `coupon_activity`：优惠券活动

| 字段 | 含义 | 核心链路关注点 |
|---|---|---|
| `id` | 活动 ID | Redis Key 和 Kafka 消息的业务主键 |
| `venue_id` | 所属景点 | 运营者只能管理 JWT 中 `venueId` 对应的数据 |
| `name` | 活动及券名称 | 发券时复制到游客券快照 |
| `threshold_amount` | 使用门槛 | 必须大于等于优惠金额 |
| `discount_amount` | 固定优惠金额 | 必须大于 0 |
| `total_stock` | 总发行量 | 只表示最初发行量，Redis 恢复时不能直接使用它 |
| `remaining_stock` | MySQL 最终剩余量 | 消费端必须通过 `remaining_stock > 0` 条件扣减 |
| `claim_start_at` | 开始领取时间 | Lua 必须校验 `[start, end)` 时间窗口 |
| `claim_end_at` | 结束领取时间 | 到点后不再接受请求 |
| `valid_from` | 券生效时间 | 发券时复制到 `user_coupon` |
| `valid_until` | 券失效时间 | 发券时复制，订单锁券时再次校验 |
| `status` | 活动状态 | DRAFT/PUBLISHED/ENDED/CANCELLED |
| `cache_ready` | 是否完成 Redis 预热 | 发布后为 0，完整预热成功后才能改为 1 |
| `preheated_at` | 最近成功预热时间 | 便于排查和重新预热 |
| `created_by` | 创建运营者 | 审计字段 |

关键索引：

```text
(venue_id, status, claim_start_at, claim_end_at)
(status, cache_ready, claim_start_at)
```

第二个索引用于预热任务扫描“已发布、未预热、即将开始”的活动。

### 4.2 `user_coupon`：游客真正持有的券

| 字段 | 含义 |
|---|---|
| `id` | 游客优惠券 ID，订单使用时传 `userCouponId` |
| `activity_id` | 来源活动 |
| `user_id` | 券所属游客账号 |
| `venue_id` | 适用景点 |
| `coupon_name` | 领取时名称快照 |
| `threshold_amount` | 领取时门槛快照 |
| `discount_amount` | 领取时优惠金额快照 |
| `valid_from` / `valid_until` | 领取时有效期快照 |
| `status` | AVAILABLE/LOCKED/USED/EXPIRED |
| `acquired_at` | 领取成功时间 |
| `used_at` | 最近正式使用时间 |

唯一约束：

```text
UNIQUE(activity_id, user_id)
```

Redis 的一人一单用于入口快速拒绝；这个数据库唯一约束才是最终防线。即使 Kafka 重复投递或者 Redis 数据丢失，也不能重复发券。

活动资料后续即使变化或活动被取消，`user_coupon` 的名称、门槛、优惠金额和有效期快照都不修改。

### 4.3 `coupon_claim_request`：异步请求结果

| 字段 | 含义 |
|---|---|
| `request_id` | 抢券请求号，也是 Kafka 消费幂等键 |
| `activity_id` | 目标活动 |
| `user_id` | 发起游客 |
| `status` | PENDING/SUCCESS/FAILED |
| `user_coupon_id` | 成功时生成的游客券 ID |
| `failure_reason` | SOLD_OUT、ALREADY_CLAIMED 等业务失败原因 |
| `requested_at` | 请求时间；消费者可用它校验当时是否处于活动窗口 |
| `processed_at` | 处理完成时间 |

约束：

```text
PRIMARY KEY(request_id)
UNIQUE(activity_id, user_id)
```

`request_id` 解决 Kafka 重复消息；`activity_id + user_id` 解决游客换请求号重复领取。

### 4.4 `booking_order` 的优惠券字段

| 字段 | 含义 |
|---|---|
| `user_coupon_id` | 本单使用的游客优惠券，可为空 |
| `original_amount` | 所有订单明细价格之和，即优惠前金额 |
| `discount_amount` | 下单时优惠金额快照 |
| `total_amount` | 最终应付金额 |

金额关系：

```text
total_amount = original_amount - discount_amount
```

当前活动规则保证 `threshold_amount >= discount_amount`，订单达到门槛后不会出现负数金额。

## 5. 三组状态转换

### 5.1 活动状态

```text
DRAFT --发布--> PUBLISHED --领取结束--> ENDED
  |                    |
  └------取消----------┴------取消------> CANCELLED
```

- `DRAFT`：可修改规则和发行量。
- `PUBLISHED`：规则被冻结，等待预热或正在领取。
- `ENDED`、`CANCELLED`：终态。
- 发布只更新 MySQL，不直接操作 Redis。
- 预热成功不改变活动状态，只把 `cache_ready` 改为 1。

### 5.2 游客优惠券状态

```text
AVAILABLE --创建订单--> LOCKED --支付成功--> USED
    |                      |                  |
    | 到期                 | 取消/超时        | 整单退款
    v                      v                  v
 EXPIRED          AVAILABLE 或 EXPIRED  AVAILABLE 或 EXPIRED
```

`LOCKED` 的意义是防止游客把同一张券同时用于多个待支付订单。券状态变化必须和订单状态、库存及票券变化处于同一个 MySQL 事务，不能通过 Kafka 延迟处理。

### 5.3 抢券请求状态

```text
PENDING --> SUCCESS
       └-> FAILED
```

- 业务失败，例如售罄、重复领取，写 `FAILED` 后提交事务，不再重试。
- MySQL、网络等技术异常应回滚事务并让 Kafka 重试。
- `SUCCESS` 和 `FAILED` 都是终态。

## 7. 订单模块如何使用优惠券

入口位于 `BookingServiceImpl#createInTransaction`：

1. 后端根据场次票种价格计算 `originalAmount`。
2. 如果请求带 `userCouponId`，通过 `SessionService` 获取场次所属 `venueId`。
3. 调用 `CouponOrderService.lockForOrder`。
4. 校验券属于当前游客、适用当前景点、状态为 AVAILABLE、处于有效期且达到门槛。
5. 执行带条件的 UPDATE，把 AVAILABLE 改成 LOCKED。
6. 保存 `originalAmount`、`discountAmount` 和最终 `totalAmount`。

支付、取消和退款：

```text
支付成功：LOCKED -> USED
用户取消：LOCKED -> AVAILABLE/EXPIRED
超时关闭：LOCKED -> AVAILABLE/EXPIRED
整单退款：USED -> AVAILABLE/EXPIRED
```

这些调用都在 `BookingServiceImpl` 的订单事务内部。优惠券状态条件更新失败时会抛出异常，使订单、票券和库存一起回滚。

## 8. 建议的 Redis 数据结构

正式设计已有以下 Key：

```text
coupon:activity:{activityId}:stock
coupon:activity:{activityId}:enabled
coupon:activity:{activityId}:claimed-users
coupon:activity:{activityId}:user-request:{userId}
coupon:claim:{requestId}
```

建议在实现 Lua 时再增加活动元数据 Hash，避免每次请求查询 MySQL：

```text
coupon:activity:{activityId}:meta
  status=PUBLISHED
  claimStartAt=<epochMillis>
  claimEndAt=<epochMillis>
```

各 Key 的职责：

- `stock`：Lua 原子预扣的入口库存。
- `enabled`：活动是否允许进入领取逻辑；取消、结束或预热不完整时为 0。
- `claimed-users`：已经取得该活动请求资格的 userId 集合。
- `user-request:{userId}`：同一游客重复请求时返回原 requestId。
- `claim:{requestId}`：提供 PENDING/SUCCESS/FAILED 的快速轮询结果。
- `meta`：Lua 校验活动状态与领取时间。

所有 Key 都应设置合理过期时间，至少覆盖领取结束时间、Kafka 最大重试周期和结果查询保留期。

## 9. 当前自动预热实现

已经创建的组件：

```text
CouponPreheatTask
CouponPreheatService
CouponPreheatServiceImpl
```

当前流程：

1. `CouponPreheatTask` 使用 `fixedDelay = 10000`，每轮结束 10 秒后再次扫描。
2. 预热窗口固定为当前时间之后 10 分钟，由 `CouponConstant.window` 定义。
3. Mapper 查询所有满足 `PUBLISHED`、`cache_ready=0`、`remaining_stock>0`、尚未结束且已进入预热窗口的活动；当前 MVP 不限制单轮批量大小。
4. 每个活动通过 Redisson 活动级锁执行，未取得锁时直接交给其他实例处理。
5. 先写 `enabled=0`，再以数据库 `remaining_stock` 写库存，并写入活动状态和领取时间元数据。
6. 条件更新数据库 `cache_ready=1` 和 `preheated_at`，成功后最后写 `enabled=1` 开放 Redis 入口。
7. Redis Key 的 TTL 保留到活动领取结束后一天。

这套代码只负责活动首次开抢前预热，不是 Redis 数据丢失后的完整恢复方案。首次预热时游客防重集合自然为空，因此不会从 MySQL 回填 `claimed-users`。如果以后支持活动进行中的 Redis 恢复，仍不能直接使用 `total_stock`，而要以 `remaining_stock` 为基础，并结合已有 `user_coupon` 和抢券请求重建防重数据。

预热完成与开抢不是同一个概念。即使提前预热成功，Lua 仍然必须校验当前时间是否已经到达 `claim_start_at`。

## 10. Lua 脚本的原子职责

建议脚本输入：

```text
KEYS: stock、enabled、claimedUsers、userRequest、claimResult、meta
ARGV: activityId、userId、requestId、nowEpochMillis、结果TTL
```

脚本应在一次原子执行中完成：

1. 检查活动入口是否启用。
2. 检查活动状态和当前时间是否处于 `[claimStartAt, claimEndAt)`。
3. 检查游客是否已经提交过；如果是，返回原 requestId，而不是创建第二个请求。
4. 检查库存是否大于 0。
5. 库存减 1。
6. 记录游客、requestId 和 PENDING 结果。
7. 返回“首次受理”或“重复请求”等明确结果码。

建议返回码示例：

```text
0  ACCEPTED
1  DUPLICATE，附原 requestId
2  SOLD_OUT
3  NOT_STARTED
4  ENDED_OR_CANCELLED
5  CACHE_NOT_READY
```

Lua 只负责 Redis 原子性，不能替代 MySQL 唯一约束和条件库存更新。

## 11. Kafka 消息与消费者事务

Topic：

```text
coupon-claim-commands-v1
```

建议消息体：

```json
{
  "requestId": "CP20260810000001",
  "activityId": 1001,
  "userId": 7,
  "requestedAt": "2026-08-10T10:00:00",
  "schemaVersion": 1
}
```

消费者收到消息后，在一个 MySQL 本地事务中完成：

1. 按 `requestId` 查询是否已经处理；若已是 SUCCESS/FAILED，直接幂等返回。
2. 建立或读取 `coupon_claim_request`。
3. 使用带条件 SQL 扣减数据库活动库存：

```sql
UPDATE coupon_activity
SET remaining_stock = remaining_stock - 1
WHERE id = #{activityId}
  AND status = 'PUBLISHED'
  AND remaining_stock > 0
  AND claim_start_at <= #{requestedAt}
  AND claim_end_at > #{requestedAt};
```

4. 插入 `user_coupon`，复制活动规则快照。
5. 把请求改为 SUCCESS，并写入 `user_coupon_id` 和 `processed_at`。
6. 提交数据库事务后再确认 Kafka offset。
7. 事务提交后更新 Redis 快速查询结果。

如果数据库库存条件更新为 0：

- 活动已取消或结束、数据库已售罄等属于业务失败。
- 把请求写成 FAILED 并提交，不抛异常重试。
- 必要时补偿之前的 Redis 预扣和游客占位。

如果数据库连接异常、死锁或程序异常：

- 让本地事务回滚。
- 抛出异常让 Kafka 重试。
- 不能先确认 offset。

## 12. 消费端幂等的三层防线

第一层：`request_id` 主键。

- 同一 Kafka 消息重复投递时，只处理一次。

第二层：`UNIQUE(activity_id, user_id)`。

- 游客更换 requestId 或防重数据异常时，仍不能重复发券。

第三层：带条件库存更新。

- 无论 Redis 是否准确，MySQL 库存都不能减到 0 以下。

处理唯一键冲突时不要一律当技术异常重试：如果已经存在同一活动、同一游客的券，应读取已有券和请求状态，按幂等结果结束。

## 13. Redis、Kafka、MySQL 之间的失败窗口

### Lua 成功，但 Kafka 尚未确认发送

Lua 会把可重建 Kafka 命令的数据与库存扣减、用户资格一起原子写入 Redis Outbox。Broker 确认后删除 Outbox；应用宕机或发送失败时保留记录，由定时任务使用相同 requestId 补发。重复消息继续由消费端幂等处理，因此不会在发送结果不确定时提前恢复库存。

### Kafka 重复投递

依靠 requestId、数据库唯一约束和消费者状态检查幂等处理。

### MySQL 扣减失败，但 Redis 已预扣

业务失败提交后，需要补偿 Redis 库存或由对账任务修正；补偿必须校验 requestId，避免删除其他新请求的数据。

### 消费成功，但 Redis 结果未更新

数据库已经是最终结果，游客结果查询应能回源 MySQL；对账或重试任务可重新写 Redis 结果。

## 15. 实现时必须守住的业务不变量

- 运营者不能管理其他景点的活动。
- 只有 PUBLISHED 且位于领取时间窗口的活动可以接受请求。
- `cache_ready=false` 时不能抢券。
- Redis 库存不能小于 0。
- MySQL `remaining_stock` 不能小于 0。
- 同一活动、同一游客最多生成一张 `user_coupon`。
- Kafka 重复消息不能重复扣库存或重复发券。
- PENDING 只能转换为 SUCCESS 或 FAILED。
- 活动取消不影响已经发放的游客券。
- 优惠券规则使用领取时快照，不能在下单时重新读取活动当前规则。
- 订单券状态变化必须与订单状态变化处于同一事务。
- 任何缓存结果与数据库冲突时，以 MySQL 最终数据为准。

## 16. 建议重点测试的场景

- 100 个线程抢 10 张券，最终最多 10 个 SUCCESS。
- 同一游客并发请求多次，只得到一个 requestId 和一张券。
- Lua 成功后 Kafka Producer 抛出异常。
- Kafka 同一消息重复消费 2～3 次。
- Consumer 扣库存后、发券前抛异常，事务应整体回滚。
- Redis 显示有库存，但 MySQL 已无库存。
- 活动在抢券请求到达时被取消。
- 活动进入开始前 10 分钟后能够被定时任务首次预热。
- Redis 数据丢失后的恢复暂不属于当前预热代码的能力，后续实现恢复功能时再补对应测试。
- 消费成功但 Redis 结果仍为 PENDING，查询应回源数据库得到 SUCCESS。
- 优惠券锁定期间订单超时，券恢复为 AVAILABLE；若已经过期则变为 EXPIRED。
