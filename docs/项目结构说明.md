# 项目结构说明

项目采用 Maven 多模块组织，按用户、景点和订单领域分别部署服务，通过 Gateway 统一对外提供接口。

```text
tourism-ticketing-platform/
├── tourism-common/         通用响应、异常、常量和工具
├── tourism-pojo/           Entity、DTO、VO、枚举和远程契约 DTO
├── tourism-gateway/        统一入口、JWT 校验和服务路由
├── tourism-user-service/   认证、用户和参观人
├── tourism-venue-service/  景点、场次、票种、目录和库存预留
├── tourism-coupon-service/ 优惠券活动、抢券、券状态和 Kafka 消费
└── tourism-order-service/  订单、电子票、核销、统计和 Flyway 迁移
```

## 服务边界

- `user-service` 管理账号和参观人资料；订单服务通过内部接口读取当前游客可下单的参观人快照。
- `venue-service` 管理景点、场次、票种和库存；订单服务通过 OpenFeign 获取下单上下文，并执行库存 TCC 的 Try、Confirm、Cancel。
- `coupon-service` 管理活动、异步抢券和游客优惠券；订单服务通过粗粒度 Try、Confirm、Cancel 接口完成订单用券。
- `order-service` 保持订单、电子票和核销为本地事务域；统计暂时保留在该服务。
- `gateway` 校验外部请求的 JWT，并拒绝直接访问 `/internal/**`；内部调用使用 `X-Service-Token`，服务发现不依赖固定端口。

## 模块约定

`tourism-common` 不承载具体业务逻辑；`tourism-pojo` 中的 Entity 不直接作为 HTTP 响应返回。跨服务调用使用 `tourism-pojo` 的远程契约 DTO，不暴露下游服务内部 Entity、Mapper 或 Service 实现。

每个服务的 MyBatis XML 放在其 `src/main/resources/mapper/<domain>/` 目录。数据库结构当前由 `tourism-order-service/src/main/resources/db/migration/` 中的 Flyway 脚本统一维护；已执行的版本化迁移不得修改或删除。
