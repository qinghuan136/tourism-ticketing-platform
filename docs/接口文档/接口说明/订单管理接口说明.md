# 订单管理接口说明

对应的 OpenAPI 文件：[booking-openapi.json](../接口json/booking-openapi.json)。

当前 MVP 提供游客端下单、订单查询、模拟支付、取消和整单退款，以及运营端订单查询接口。订单不能直接修改或删除，状态只能由明确的业务事件驱动。

## 通用业务规则

- 游客端接口只能访问当前登录游客自己的订单，`userId` 从 JWT 登录信息获取。
- 运营端接口只能查询当前登录账号所属景点的订单，`venueId` 从 JWT 登录信息获取。
- 一个订单只对应一个场次，可包含多个“参观人 + 场次票种”明细。
- 订单金额由后端按照 `session_ticket_type.sale_price` 计算，前端不能提交订单金额。
- 创建订单时保存参观人、证件、票种名称和成交价格快照，后续资料变化不修改历史订单。
- 接口返回的证件号码必须脱敏。
- 创建、支付、取消、超时关闭和退款涉及的订单、库存与票券变化必须处于同一事务。
- 所有库存更新必须同时校验场次 `remaining_capacity` 和票种 `remaining_quantity`，避免超卖或重复归还。

## 1. 创建订单

```http
POST /tourist/orders
Authorization: Bearer <token>
Content-Type: application/json
```

请求示例：

```json
{
  "sessionId": 21,
  "userCouponId": 2001,
  "items": [
    {
      "visitorId": 101,
      "sessionTicketTypeId": 301
    },
    {
      "visitorId": 102,
      "sessionTicketTypeId": 302
    }
  ]
}
```

业务规则：

- 场次必须处于 `OPEN` 状态，当前时间必须处于预约窗口内。
- 参观人必须存在、属于当前游客并处于 `ACTIVE` 状态。
- 场次票种必须属于目标场次、处于 `ON_SALE` 状态且余量充足。
- 同一个参观人不能在同一订单中重复出现。
- 同一场次与同一参观人不能同时存在于 `PENDING_PAYMENT`、`PAID`、`REFUNDING` 或 `COMPLETED` 订单中，所选票种不同也不能重复下单。
- 原订单取消、超时关闭或退款后，该参观人才允许重新购买当前场次。
- `userCouponId` 可选；传入时优惠券必须属于当前游客、适用于场次所属景点、处于 `AVAILABLE` 状态且订单优惠前金额达到使用门槛。
- 一笔订单最多使用一张优惠券。创建订单时通过条件更新将优惠券改为 `LOCKED`，并保存优惠前金额、优惠金额和最终应付金额。
- 后端计算数量和总金额，并写入订单明细快照。
- 创建时同时扣减场次剩余容量和各票种剩余数量，任一扣减失败则整笔订单回滚。
- 总金额大于 `0` 时创建为 `PENDING_PAYMENT` 并设置 `expireAt`。
- 总金额等于 `0` 时直接创建为 `PAID`，并为每条明细生成电子票。
- 返回订单 ID、订单号、优惠前金额、优惠金额、最终应付金额、状态和支付截止时间。

## 2. 分页查询我的订单

```http
GET /tourist/orders?page=1&size=20&status=PAID
Authorization: Bearer <token>
```

- `page` 默认 `1`，`size` 默认 `20`，最大 `100`。
- `status` 为可选条件。
- 只返回当前游客自己的订单，按创建时间倒序排列。

## 3. 获取我的订单详情

```http
GET /tourist/orders/{orderId}
Authorization: Bearer <token>
```

返回订单头、场次信息、订单明细、状态时间和已经生成的票券概要。订单不存在或不属于当前游客时统一返回 `NOT_FOUND`。

## 4. 支付订单

```http
POST /tourist/orders/{orderId}/pay
Authorization: Bearer <token>
```

当前 MVP 使用模拟支付，不接收支付密码或客户端生成的支付流水号。

业务规则：

- 只有 `PENDING_PAYMENT` 订单可以支付。
- 当前时间必须早于 `expireAt`；已经超时的订单先关闭并归还库存，再返回冲突错误。
- 支付成功后写入后端生成的 `paymentNo` 和 `paidAt`，状态变为 `PAID`。
- 使用优惠券的订单支付成功时，将优惠券从 `LOCKED` 改为 `USED`。
- 每条订单明细生成一张电子票，重复请求不能重复生成票券。

## 5. 取消待支付订单

```http
POST /tourist/orders/{orderId}/cancel
Authorization: Bearer <token>
```

- 只有 `PENDING_PAYMENT` 订单可以取消。
- 状态变为 `CANCELLED`，记录 `cancelledAt`。
- 归还场次容量和各票种余量。
- 已锁定优惠券未过期时恢复为 `AVAILABLE`，已过期时改为 `EXPIRED`。
- 已支付订单不能取消，需要使用退款接口。

## 6. 整单退款

```http
POST /tourist/orders/{orderId}/refund
Authorization: Bearer <token>
```

当前提供分阶段整单退款，不提供部分退款或人工审核。本地环境使用 Redis 模拟退款平台，网关接口可替换为真实支付平台实现。

业务规则：

- 只有 `PAID` 订单可以退款。
- 场次必须尚未开始，且订单中不能存在 `USED` 票券。
- 第一段事务将订单变为 `REFUNDING`，保存唯一 `refundNo`，并将有效票券冻结为 `REFUNDING`。
- 退款平台明确成功后，第二段事务将订单变为 `REFUNDED`、记录 `refundAt`，并将票券改为 `VOID`。
- 只有退款成功后才归还场次容量和各票种余量。
- 使用过的优惠券未过期时恢复为 `AVAILABLE`，已过期时改为 `EXPIRED`。
- 退款结果超时时订单保持 `REFUNDING`，由后台使用原 `refundNo` 对账；明确失败时恢复为 `PAID` 并解冻票券。

## 7. 运营端分页查询订单

```http
GET /operator/orders?page=1&size=20&status=PAID&orderNo=202608010001&sessionId=21&visitDate=2026-08-01
Authorization: Bearer <token>
```

- 允许 `OPERATOR` 和 `STAFF` 访问。
- 只查询当前账号所属景点的订单。
- `status`、`orderNo`、`sessionId` 和 `visitDate` 均为可选条件。
- `orderNo` 使用精确查询，当前 MVP 不提供复杂搜索或导出。

## 8. 运营端获取订单详情

```http
GET /operator/orders/{orderId}
Authorization: Bearer <token>
```

返回当前景点订单的游客概要、订单明细、支付信息和票券状态。订单不存在或不属于当前景点时统一返回 `NOT_FOUND`。

运营端暂不提供通用订单状态修改接口，也不能直接删除订单。

## 订单状态机

订单初始状态由创建结果决定：付费订单为 `PENDING_PAYMENT`，零元订单直接为 `PAID`。后续状态只允许按照下表转换：

| 当前状态 | 事件 | 下一状态 | 主要副作用 |
|---|---|---|---|
| `PENDING_PAYMENT` | `PAY_SUCCESS` | `PAID` | 记录支付信息、生成电子票并核销优惠券 |
| `PENDING_PAYMENT` | `USER_CANCEL` | `CANCELLED` | 归还库存并释放优惠券 |
| `PENDING_PAYMENT` | `PAYMENT_TIMEOUT` | `CLOSED` | 归还库存并释放优惠券 |
| `PAID` | `REFUND_REQUESTED` | `REFUNDING` | 保存退款单号并冻结票券 |
| `REFUNDING` | `REFUND_SUCCESS` | `REFUNDED` | 作废票券、归还库存并按有效期退回优惠券 |
| `REFUNDING` | `REFUND_FAILED` | `PAID` | 解冻票券，不归还库存 |
| `PAID` | `FULFILLMENT_FINISHED` | `COMPLETED` | 场次结束后由后台任务收口 |

`CANCELLED`、`CLOSED`、`COMPLETED` 和 `REFUNDED` 均为终态。支付失败不会改变订单状态。

状态机只负责从“当前状态 + 事件”推导下一状态。支付期限、退款时间、票券是否核销、库存扣减与归还等业务条件由 Booking Service 校验。数据库更新应携带原状态条件，防止同一订单事件被并发重复执行。

## 后台处理

- 定时关闭超过 `expireAt` 的 `PENDING_PAYMENT` 订单，触发 `PAYMENT_TIMEOUT`。
- 定时扫描超过等待时间的 `REFUNDING` 订单，按原 `refundNo` 查询或补发退款。
- 场次结束后，后台任务先将尚未使用的有效票券变为 `EXPIRED`，再将对应的 `PAID` 订单收口为 `COMPLETED`。

## MVP 暂不提供

- 订单修改、物理删除和批量操作。
- 部分退款和退款申请审核。
- 真实第三方支付下单与回调。
- 运营端手工修改订单状态。
- 订单导出、统计报表和复杂搜索。
