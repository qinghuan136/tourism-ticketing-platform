# 优惠券秒杀业务与表设计

本文定义优惠券秒杀 MVP 的领域边界、数据结构和一致性规则。接口定义见 [优惠券秒杀接口说明](../接口文档/接口说明/优惠券秒杀接口说明.md)。

## 1. 模块边界

- 优惠券秒杀负责活动管理、异步领取、游客优惠券和订单用券，不负责创建票务订单。
- 每个运营者当前绑定唯一 `venueId`，优惠券活动只能发布到该景点。
- Kafka 只用于异步发券；订单用券通过 order-service 与 coupon-service 的同步轻量 TCC 完成。
- Redis 负责入口库存预扣和防重复请求，MySQL 是活动库存、领取结果和优惠券状态的最终数据源。

## 2. 优惠券活动表 `coupon_activity`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT UNSIGNED | PK，自增 | 活动 ID |
| `venue_id` | BIGINT UNSIGNED | NOT NULL，FK | 所属景点 |
| `name` | VARCHAR(100) | NOT NULL | 活动及优惠券名称 |
| `threshold_amount` | DECIMAL(10,2) | NOT NULL | 使用门槛 |
| `discount_amount` | DECIMAL(10,2) | NOT NULL | 固定优惠金额 |
| `total_stock` | INT UNSIGNED | NOT NULL | 总发行量 |
| `remaining_stock` | INT UNSIGNED | NOT NULL | 数据库最终剩余量 |
| `claim_start_at` | DATETIME | NOT NULL | 开始领取时间 |
| `claim_end_at` | DATETIME | NOT NULL | 结束领取时间 |
| `valid_from` | DATETIME | NOT NULL | 优惠券生效时间 |
| `valid_until` | DATETIME | NOT NULL | 优惠券失效时间 |
| `status` | VARCHAR(20) | NOT NULL | DRAFT/PUBLISHED/ENDED/CANCELLED |
| `cache_ready` | TINYINT(1) | NOT NULL，默认 0 | Redis 领取数据是否已完成预热 |
| `preheated_at` | DATETIME | NULL | 最近一次成功预热时间 |
| `created_by` | BIGINT UNSIGNED | NOT NULL，FK | 创建运营者 |
| `created_at` | DATETIME | NOT NULL | 创建时间 |
| `updated_at` | DATETIME | NOT NULL | 修改时间 |

必要约束和索引：

```text
CHECK (threshold_amount >= discount_amount AND discount_amount > 0)
CHECK (total_stock > 0 AND remaining_stock <= total_stock)
CHECK (claim_start_at < claim_end_at)
CHECK (valid_from < valid_until AND valid_until > claim_start_at)
INDEX (venue_id, status, claim_start_at, claim_end_at)
INDEX (status, cache_ready, claim_start_at)
```

发布后不得修改优惠规则、库存和时间字段。发布只完成数据库 `DRAFT -> PUBLISHED`，并保持 `cache_ready = 0`；开抢前自动预热成功后，核心链路再写入 `cache_ready = 1` 和 `preheated_at`。活动结束状态可以由后台任务更新，但领取接口始终同时校验状态和时间，避免任务延迟造成错误领取。

## 3. 游客优惠券表 `user_coupon`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT UNSIGNED | PK，自增 | 游客优惠券 ID |
| `activity_id` | BIGINT UNSIGNED | NOT NULL，FK | 来源活动 |
| `user_id` | BIGINT UNSIGNED | NOT NULL，FK | 领取游客账号 |
| `venue_id` | BIGINT UNSIGNED | NOT NULL，FK | 适用景点 |
| `coupon_name` | VARCHAR(100) | NOT NULL | 名称快照 |
| `threshold_amount` | DECIMAL(10,2) | NOT NULL | 门槛快照 |
| `discount_amount` | DECIMAL(10,2) | NOT NULL | 优惠金额快照 |
| `valid_from` | DATETIME | NOT NULL | 生效时间快照 |
| `valid_until` | DATETIME | NOT NULL | 失效时间快照 |
| `status` | VARCHAR(20) | NOT NULL | AVAILABLE/LOCKED/USED/EXPIRED |
| `acquired_at` | DATETIME | NOT NULL | 领取时间 |
| `used_at` | DATETIME | NULL | 最近一次正式使用时间 |
| `locked_order_id` | BIGINT UNSIGNED | NULL | 当前锁券所属订单，用于 Try/Cancel 幂等 |
| `used_order_id` | BIGINT UNSIGNED | NULL | 正式核销所属订单，用于 Confirm/退款恢复幂等 |
| `created_at` | DATETIME | NOT NULL | 创建时间 |
| `updated_at` | DATETIME | NOT NULL | 修改时间 |

必要约束和索引：

```text
UNIQUE (activity_id, user_id)
INDEX (user_id, status, valid_until)
INDEX (venue_id, status)
```

活动字段写入游客优惠券快照后，活动资料变化或取消都不能追溯修改已经发放的优惠券。

## 4. 抢券请求表 `coupon_claim_request`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `request_id` | VARCHAR(64) | PK | 异步请求号 |
| `activity_id` | BIGINT UNSIGNED | NOT NULL，FK | 目标活动 |
| `user_id` | BIGINT UNSIGNED | NOT NULL，FK | 请求游客 |
| `status` | VARCHAR(20) | NOT NULL | PENDING/SUCCESS/FAILED |
| `user_coupon_id` | BIGINT UNSIGNED | NULL，FK | 成功生成的优惠券 |
| `failure_reason` | VARCHAR(50) | NULL | 业务失败原因 |
| `requested_at` | DATETIME | NOT NULL | 请求时间 |
| `processed_at` | DATETIME | NULL | 完成时间 |
| `created_at` | DATETIME | NOT NULL | 创建时间 |
| `updated_at` | DATETIME | NOT NULL | 修改时间 |

必要约束和索引：

```text
UNIQUE (activity_id, user_id)
INDEX (status, created_at)
```

`request_id` 用于 Kafka 消费幂等，`activity_id + user_id` 用于阻止同一游客通过多个请求号重复领取。

## 5. 订单表调整

`booking_order` 新增：

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_coupon_id` | BIGINT UNSIGNED NULL | 使用的游客优惠券 |
| `original_amount` | DECIMAL(10,2) NOT NULL | 优惠前金额 |
| `discount_amount` | DECIMAL(10,2) NOT NULL DEFAULT 0 | 优惠金额 |

现有 `total_amount` 保持为最终应付金额：

```text
total_amount = max(original_amount - discount_amount, 0)
```

`user_coupon_id` 不设置唯一约束。订单取消、超时或退款后优惠券可能恢复可用，并被后续订单再次使用；历史订单仍需保留原优惠券引用和金额快照。建议增加普通索引 `INDEX(user_coupon_id)`。

数据库落地时新增版本化迁移，例如 `V4__add_coupon_feature.sql`，不要修改已有迁移。迁移顺序建议为：先创建 `coupon_activity`，再创建 `user_coupon` 和 `coupon_claim_request`，最后扩展 `booking_order`。历史订单的 `original_amount` 先回填为原 `total_amount`，`discount_amount` 回填为 `0`，完成回填后再增加非空约束。

## 6. Redis 数据

```text
coupon:activity:{activityId}:stock                  活动入口剩余库存
coupon:activity:{activityId}:enabled                领取入口是否启用
coupon:activity:{activityId}:claimed-users          已提交游客集合
coupon:activity:{activityId}:user-request:{userId}  游客对应的 requestId
coupon:claim:{requestId}                            PENDING/SUCCESS/FAILED
```

Lua 脚本原子完成活动校验、重复校验、库存预扣和请求占位。Redis 重启或数据丢失时不得使用 `total_stock` 重新初始化，应根据数据库 `remaining_stock` 和已存在请求恢复。

当前 MVP 的预热任务每轮结束 10 秒后再次扫描，预热当前时间之后 10 分钟内即将开始的活动。查询条件为 `PUBLISHED`、`cache_ready = 0`、`remaining_stock > 0`、尚未结束且已进入预热窗口，单轮暂不限制批量大小。任务先关闭 Redis 入口，再写入数据库 `remaining_stock`、活动状态和领取时间；数据库条件更新为 `cache_ready = 1` 后，最后启用 Redis 入口。首次预热时游客防重集合为空，后续由 Lua 在受理请求时写入。抢券入口必须拒绝未启用的活动，活动取消或结束后应在数据库事务提交后关闭 Redis 领取入口。

当前预热只负责开抢前首次初始化，不负责 Redis 数据丢失后的恢复。后续若增加运行中恢复，不能使用 `total_stock`，必须根据数据库 `remaining_stock`、已有游客券和抢券请求重建库存及防重数据。

## 7. Kafka 消息

Topic：`coupon-claim-commands-v1`。

```json
{
  "requestId": "CP20260810000001",
  "activityId": 1001,
  "userId": 7,
  "requestedAt": "2026-08-10T10:00:00",
  "schemaVersion": 1
}
```

消费者使用数据库本地事务完成：

1. 按 `requestId` 检查是否已经处理。
2. 使用 `remaining_stock > 0` 条件更新扣减数据库库存。
3. 插入 `user_coupon` 快照。
4. 将请求更新为 `SUCCESS` 并记录 `user_coupon_id`。
5. 提交事务后确认 Kafka offset。

重复消息依靠请求状态及两处唯一约束安全返回。库存不足、重复领取等业务失败直接写入 `FAILED`；技术异常重试，最终失败进入 `coupon-claim-commands-v1-dlt`。

当前最小死信补偿会先按 `requestId` 查询 MySQL：已有最终结果时只把该结果重新同步到 Redis；没有数据库结果时才通过 Lua 恢复 Redis 预扣库存，并删除本次请求占位和游客防重标记。这样可以避免数据库已经成功发券、但 Redis 结果同步失败时误恢复库存。

## 8. 订单一致性

创建订单时，order-service 先以订单号调用 coupon-service 的 Try 锁券接口；该接口的条件更新必须携带游客、景点、状态、有效期和订单号：

```sql
UPDATE user_coupon
SET status = 'LOCKED', locked_order_id = #{orderId}, updated_at = NOW()
WHERE id = #{userCouponId}
  AND user_id = #{userId}
  AND venue_id = #{venueId}
  AND status = 'AVAILABLE'
  AND valid_from <= NOW()
  AND valid_until > NOW();
```

Try 成功后订单在本地事务中落库；提交成功后 Confirm，失败后 Cancel。订单侧会持久化二阶段状态并重试网络失败，coupon-service 以 `coupon_order_reservation` 和 `orderId` 保证重复 Try、Confirm、Cancel 无副作用，并定期释放长期 `LOCKED` 的券。
