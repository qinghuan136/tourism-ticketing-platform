# 优惠券秒杀三场景总测试报告

## 1. 测试结论

本轮三个场景全部通过：

- 200 个不同游客争抢 50 张优惠券时，最终只发放 50 张，没有超卖、负库存或重复发券。
- 同一游客 50 个并发请求只生成 1 条领取请求和 1 张优惠券，库存只扣减 1。
- 20 个不同游客领取后全部通过 Kafka 异步落库，最终状态均为 `SUCCESS`。

随后执行的加强与峰值测试同样通过：

- 500 个不同游客争抢 100 张券，最终发券 100 张，技术失败为 0，入口 P95 为 383ms。
- 同一游客 200 并发只生成 1 张券，库存只扣减 1。
- 200 条 Kafka 异步发券消息全部落库，最终成功率 100%，游客侧结果可见 P95 为 4.02 秒。
- 1000 个不同游客峰值争抢 200 张券，最终发券 200 张，技术失败为 0，入口 P95 为 794ms。

测试窗口内 Spring Boot 日志共检查 2555 行，没有发现 `WARN` 或 `ERROR`。

## 2. 测试环境与方法

- 测试时间：2026-08-07 20:14—20:17（Asia/Shanghai）
- 压测工具：Apache JMeter 5.6.3，非 GUI 模式
- 被测地址：`http://localhost:8080`
- 基础设施：本机 Spring Boot、MySQL、Redis、Kafka
- 测试账号：1000 个状态正常且互不相同的游客账号
- 并发方式：线程完成登录后通过同步定时器集中发起抢券请求
- 数据隔离：每个场景使用独立的新优惠券活动

本报告中的入口吞吐量按照原始 JTL 中全部抢券请求的起止窗口计算。由于测试只包含一次短促突发流量，该数值表示本机瞬时处理能力，不能直接当作生产环境的持续 TPS 上限。

## 7. 综合分析

1. 正确性是本轮最明确的结果。三个场景的库存均满足“最终库存 + 发券数量 = 初始库存”，不存在负库存和重复发券。
2. Redis Lua 正确承担了高并发入口裁决。200 个请求竞争 50 个名额时，只有 50 个请求进入异步链路，数据库没有承担 200 次写入竞争。
3. 一人一券采用幂等响应方式。重复点击不会重复扣库存或重复投递消息，同时客户端仍能获得第一次请求的编号。
4. Kafka 链路在 20 并发下全部成功，游客侧约 0.35 秒可以观察到最终结果，P99 小于 0.5 秒。
5. 500 并发加强场景和 1000 并发峰值场景均保持技术失败为 0。入口 P99 分别为 395ms 和 815ms，说明并发升高后排队明显增加，但本机测试范围内仍能正确完成入口裁决。

## 8. 限制与后续建议

- 本轮为开发机单机测试，Spring Boot、MySQL、Redis、Kafka 和 JMeter 可能共享硬件资源，结果不能直接推导生产容量。
- 吞吐量来自很短的单次突发窗口。若需要确定稳定 TPS，应增加持续压测场景，例如保持 100—200 并发运行 1—5 分钟。
- `coupon_claim_request.requested_at` 和 `processed_at` 当前使用秒级 `DATETIME`，同一秒内完成时数据库差值为 0，无法用于亚秒级性能统计；本轮因此使用 JTL 时间戳计算。
- 当前三个目标场景均已通过，MVP 阶段无需立即增加更复杂的故障注入或长时间稳定性测试。

## 11. 三消费者线程下的 1000 并发异步落库测试

### 11.1 场景与配置

主抢券 Topic 配置为 3 个分区，应用中的抢券监听容器并发度设置为 3。启动日志确认同一消费组内的 3 个消费者线程分别获得了分区 0、1、2。

本次使用独立活动 ID 11，库存设置为 1000；1000 个不同游客各发起 1 次抢券请求。线程在 5 秒内启动，并在抢券前通过同步定时器集中释放。为观察异步落库完成情况，客户端以 100ms 间隔轮询结果，最多轮询 200 次。

| 抢券请求数 | 1000 |

| 售罄响应 | 0 |
| 技术失败 | 0 |
| 入口集中窗口 | 3465ms |
| 入口窗口吞吐 | 288.60 请求/秒 |
| 入口平均响应 | 2448.87ms |

数据库核验结果：活动剩余库存为 0，`coupon_claim_request` 的 1000 条记录均为 `SUCCESS`，共生成 1000 张用户优惠券，按“活动 + 用户”统计不存在重复发券。

### 11.3 分析

三个消费线程已经实际参与消费，但吞吐没有按线程数线性提升。每一条消息最终都需要对同一条 `coupon_activity` 记录执行条件扣减：`remaining_stock = remaining_stock - 1`。该热点行的写锁会使这部分数据库更新串行化；同时，1000 个客户端持续轮询结果也会占用应用和数据库资源。因此本轮结果主要验证了三分区、三消费者下的正确消费与最终落库，而不是三倍吞吐的容量结论。

本次与 10.4 的 200 并发结果不宜直接作性能对比：后者只有 200 条消息进入 Kafka，而本次有 1000 条消息并开启了高频结果轮询。若需要单独评估消费者并发度，应在相同库存、相同消息量和相同轮询策略下分别测试并发度 1 与 3。
