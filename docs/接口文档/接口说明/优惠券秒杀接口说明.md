# 优惠券秒杀接口说明

对应的 OpenAPI 文件：[coupon-openapi.json](../接口json/coupon-openapi.json)。

当前 MVP 提供景点运营者创建、修改、发布和取消满减券秒杀活动，以及游客查询活动、异步抢券、查询抢券结果和查看本人优惠券的接口。Kafka 和 Redis 只承担内部异步削峰、库存预扣和防重复提交，不直接暴露管理接口。

## 一、核心业务规则

- 当前只支持固定金额满减券，不支持折扣券、兑换码、叠加券和指定票种券。
- 每个活动只属于一个景点。运营端所有写操作使用 JWT 登录信息中的 `venueId`，前端不能提交或修改 `venueId`。
- 每个游客账号在同一活动中最多领取一张优惠券，领取资格按游客账号计算，与参观人无关。
- 一张优惠券只能用于所属景点的一笔订单，一笔订单最多使用一张优惠券。
- 订单优惠前金额达到 `thresholdAmount` 后才能使用；最终应付金额最低为 `0`。
- 活动发布后，名称、优惠门槛、优惠金额、库存、领取时间和有效期均不可修改。
- 取消活动只停止后续领取，不作废游客已经领取的优惠券。
- 抢券接口返回 `PENDING` 只表示请求已进入异步处理链路，不代表领取成功。
- Redis 库存用于入口预扣，数据库 `remainingStock` 是最终库存依据；消费者必须通过条件更新保证库存不会小于 `0`。
- Kafka 按至少一次投递处理。消费端使用 `requestId` 和数据库唯一约束保证重复消息不会重复发券。

## 二、状态规则

### 2.1 活动状态

| 当前状态 | 操作/条件 | 下一状态 | 说明 |
|---|---|---|---|
| `DRAFT` | 发布 | `PUBLISHED` | 校验活动规则并等待开抢前自动预热 |
| `DRAFT` | 取消 | `CANCELLED` | 草稿不再使用 |
| `PUBLISHED` | 取消 | `CANCELLED` | 停止后续领取，已领取优惠券不受影响 |
| `PUBLISHED` | 领取结束时间到达 | `ENDED` | 后台任务更新，接口判断仍以时间为准 |

`CANCELLED` 和 `ENDED` 为终态。活动是否可领取还必须满足当前时间位于 `[claimStartAt, claimEndAt)` 且剩余库存大于 `0`。

### 2.2 游客优惠券状态

| 当前状态 | 业务事件 | 下一状态 |
|---|---|---|
| `AVAILABLE` | 创建订单并锁券 | `LOCKED` |
| `AVAILABLE` | 到达失效时间 | `EXPIRED` |
| `LOCKED` | 支付成功 | `USED` |
| `LOCKED` | 订单取消或超时，优惠券未过期 | `AVAILABLE` |
| `LOCKED` | 订单取消或超时，优惠券已过期 | `EXPIRED` |
| `USED` | 整单退款，优惠券未过期 | `AVAILABLE` |
| `USED` | 整单退款，优惠券已过期 | `EXPIRED` |

优惠券锁定、使用、释放必须和对应的订单状态变化处于同一数据库事务，不能通过 Kafka 延迟处理。

### 2.3 抢券请求状态

`PENDING` 只能转换为 `SUCCESS` 或 `FAILED`。业务失败不重试；数据库或网络等技术异常可以重试，超过次数后进入死信 Topic，并由补偿任务处理长期处于 `PENDING` 的请求。

## 三、运营端接口

### 3.1 分页查询活动

```http
GET /operator/coupon-activities?page=1&size=20&status=DRAFT&keyword=暑期
Authorization: Bearer <token>
```

- 只返回当前运营者所属景点的活动。
- `status` 和 `keyword` 为可选条件，`keyword` 按活动名称模糊查询。
- 按创建时间倒序返回。

### 3.2 创建活动草稿

```http
POST /operator/coupon-activities
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "name": "暑期满100减20券",
  "thresholdAmount": 100.00,
  "discountAmount": 20.00,
  "totalStock": 500,
  "claimStartAt": "2026-08-10T10:00:00",
  "claimEndAt": "2026-08-10T12:00:00",
  "validFrom": "2026-08-10T10:00:00",
  "validUntil": "2026-08-31T23:59:59"
}
```

业务规则：

- 初始状态固定为 `DRAFT`，`remainingStock` 初始化为 `totalStock`。
- `discountAmount` 必须大于 `0`，`thresholdAmount` 必须大于等于 `discountAmount`。
- `totalStock` 必须大于 `0`。
- `claimStartAt < claimEndAt`，且 `validUntil` 必须晚于 `claimStartAt`。
- 同一景点允许存在同名历史活动，活动通过 ID 区分。

### 3.3 获取活动详情

```http
GET /operator/coupon-activities/{activityId}
Authorization: Bearer <token>
```

活动不存在或不属于当前景点时统一返回 `NOT_FOUND`。

### 3.4 修改活动草稿

```http
PUT /operator/coupon-activities/{activityId}
Authorization: Bearer <token>
Content-Type: application/json
```

请求体与创建活动相同。只有 `DRAFT` 活动可以修改；`PUBLISHED`、`ENDED` 和 `CANCELLED` 均返回 `CONFLICT`。

### 3.5 发布活动

```http
POST /operator/coupon-activities/{activityId}/publish
Authorization: Bearer <token>
```

- 只有 `DRAFT` 可以发布。
- 发布时重新校验库存、领取时间和有效期。
- 发布接口只更新数据库状态，发布后 `cacheReady` 保持为 `false`。
- 自动预热任务每轮结束 10 秒后再次扫描，处理未来 10 分钟内即将开始且 `cacheReady = false` 的活动。
- 预热以数据库 `remainingStock` 初始化 Redis 库存，同时写入活动状态和领取时间；数据库 `cacheReady` 条件更新成功后再启用 Redis 领取入口。
- 抢券接口必须拒绝 Redis 入口未启用的活动，避免预热未完成时进入秒杀链路。

### 3.6 取消活动

```http
POST /operator/coupon-activities/{activityId}/cancel
Authorization: Bearer <token>
```

- `DRAFT` 和 `PUBLISHED` 可以取消。
- 取消发布中的活动时同时关闭 Redis 领取入口。
- 已领取的 `user_coupon` 保持原有效期和状态，不批量作废。

## 四、游客端接口

### 4.1 查询景点可领取活动

```http
GET /public/venues/{venueId}/coupon-activities
```

- 允许未登录访问。
- 只返回 `PUBLISHED` 且尚未超过 `claimEndAt` 的活动。
- 返回派生领取状态 `NOT_STARTED`、`IN_PROGRESS` 或 `SOLD_OUT`，不直接返回活动管理字段。

### 4.2 异步提交抢券请求

```http
POST /tourist/coupon-activities/{activityId}/claims
Authorization: Bearer <token>
```

首次被系统接受时返回 HTTP `202`：

```json
{
  "code": "SUCCESS",
  "message": "抢券请求已受理",
  "data": {
    "requestId": "CP20260810000001",
    "status": "PENDING"
  }
}
```

处理流程：

1. 校验登录角色为 `TOURIST`。
2. Redis Lua 原子校验活动时间、库存和游客是否已经提交。
3. 预扣 Redis 库存并记录 `activityId + userId -> requestId`。
4. 将包含 `requestId`、`activityId`、`userId` 和请求时间的消息发送到 Kafka。
5. 消费者在数据库事务中条件扣减库存、创建游客优惠券并更新请求结果。

同一游客重复请求同一活动时返回原 `requestId` 和当前状态，不生成新的领取资格。活动未开始、已结束、已取消或已售罄时返回 `CONFLICT`；Kafka 暂时无法接收消息时返回 `SERVICE_UNAVAILABLE`。

### 4.3 查询抢券结果

```http
GET /tourist/coupon-claims/{requestId}
Authorization: Bearer <token>
```

- 只能查询当前游客自己的请求。
- `SUCCESS` 时返回 `userCouponId`。
- `FAILED` 时返回简短失败原因，例如 `SOLD_OUT` 或 `ALREADY_CLAIMED`。
- 查询优先读取 Redis，因此刚受理但尚未落库的请求也会返回 `PENDING`；缓存不存在时再查询数据库最终结果。

### 4.4 查询我的优惠券

```http
GET /tourist/coupons?venueId=10&status=AVAILABLE&orderAmount=120.00
Authorization: Bearer <token>
```

- `venueId`、`status` 和 `orderAmount` 均为可选条件。
- 传入 `orderAmount` 时，只返回门槛不高于该金额的优惠券。
- MVP 阶段个人优惠券数量较少，不分页，按领取时间倒序返回。
- 返回名称、优惠门槛、优惠金额、有效期、所属景点和状态。

## 五、订单接口衔接

现有 `POST /tourist/orders` 增加可选字段 `userCouponId`。不传时保持原下单流程；传入时必须在订单事务中完成：

1. 校验优惠券属于当前游客且状态为 `AVAILABLE`。
2. 校验优惠券所属景点与场次所属景点一致。
3. 校验有效期和订单优惠前金额是否达到门槛。
4. 使用条件更新将优惠券从 `AVAILABLE` 改为 `LOCKED`。
5. 保存 `originalAmount`、`discountAmount` 和最终 `totalAmount`。

支付成功时将优惠券改为 `USED`；订单取消、超时或整单退款时，根据有效期恢复为 `AVAILABLE` 或改为 `EXPIRED`。这些变化必须和订单、票券及库存变化处在同一个事务。

## 六、当前实现边界

已落地的业务包括活动草稿管理、公开活动与游客优惠券查询、订单用券、Redis Lua 防超卖与一人一单、自动预热、Kafka 异步发券、消费端数据库幂等，以及 Producer 发送失败和消费死信的基础补偿。

主消费者发生技术异常时会间隔一秒重试两次，仍失败则进入 `coupon-claim-commands-v1-dlt`。死信消费者先查询 MySQL：数据库已有最终结果时只修复 Redis 查询结果；没有数据库结果时才恢复 Redis 预扣并把请求标记为 `FAILED`。当前 MVP 暂不提供独立补偿任务表、人工重放后台和全量对账平台。

## 七、Kafka 消费规则

- Topic：`coupon-claim-commands-v1`；死信 Topic：`coupon-claim-commands-v1-dlt`。
- 消息使用 JSON，业务键至少包含 `requestId`、`activityId`、`userId`、`requestedAt` 和 `schemaVersion`。
- 消费者在事务开始后先按 `requestId` 查询结果；已是 `SUCCESS` 或 `FAILED` 时直接结束，保证重复消费幂等。
- 发券依赖数据库唯一约束 `UNIQUE(activity_id, user_id)`，库存使用 `remaining_stock > 0` 的条件更新。
- 数据库事务提交后才能确认 Kafka offset。
- 业务失败直接记为 `FAILED`；技术失败重试，超过次数进入死信 Topic。
- DLT 补偿必须先查询 MySQL 最终状态，不能收到死信后直接恢复库存。

## 七、MVP 暂不提供

- 百分比折扣券、兑换码、券包、指定票种券和优惠叠加。
- 管理员手工发券、转赠优惠券和游客主动删除优惠券。
- 活动发布后的编辑、补库存和修改领取时间。
- WebSocket 或 SSE 实时推送抢券结果，前端使用轮询查询。
- 独立优惠券微服务、跨景点通用券和复杂营销规则引擎。
