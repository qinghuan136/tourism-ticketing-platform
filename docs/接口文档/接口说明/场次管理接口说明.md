# 场次管理接口说明

对应的 OpenAPI 文件：[session-openapi.json](../接口json/session-openapi.json)。

当前 MVP 提供当前景点场次的分页查询、详情、新建、修改、事件驱动状态流转和删除接口。所有接口仅允许景点运营者访问，景点 ID 从 JWT 登录信息中的 `venueId` 获取，前端不传递 `venueId`。

## 通用业务规则

- 所有查询和写操作都必须限定在当前运营者所属景点内。
- 场次保留总容量硬上限，同时由运营者为每个票种分配独立数量。
- `totalCapacity` 必须大于 `0`。新建场次时 `remainingCapacity` 由后端初始化为 `totalCapacity`，前端不能直接传递。
- 每个票种的 `allocatedQuantity` 必须大于 `0`，同一场次所有票种分配数量之和不能超过 `totalCapacity`；允许小于总容量，差额作为暂未分配容量。
- 新建或修改草稿场次时，每个票种的 `remainingQuantity` 由后端初始化为 `allocatedQuantity`，前端不能直接传递。
- 后续下单必须同时扣减场次 `remainingCapacity` 和对应票种 `remainingQuantity`，任一余量不足都不能创建订单。
- `startTime` 必须早于 `endTime`。
- `bookingStartAt` 必须早于 `bookingEndAt`，且 `bookingEndAt` 不能晚于场次的入场开始时间。
- 同一景点不能存在参观日期、开始时间和结束时间完全相同的场次；当前 MVP 不禁止时间段部分重叠。
- 场次选择的票种必须存在、属于当前景点并处于 `ENABLED` 状态，同一场次不能重复选择同一票种。
- 每个场次票种配置包含该场次的实际售价 `salePrice`。该价格不会随着 `ticket_type.base_price` 后续变化而自动改变。
- 场次查询返回 `sessionTicketTypeId`，它对应 `session_ticket_type.id`，游客创建订单时应提交该 ID，而不是普通的 `ticketTypeId`。
- 新建、修改场次及维护 `session_ticket_type` 必须在同一事务中完成。

## 分页查询场次

```http
GET /operator/sessions?page=1&size=20&visitDate=2026-08-01&status=OPEN
Authorization: Bearer <token>
```

用于场次管理列表。

- `visitDate` 和 `status` 均为可选条件。
- `page` 默认 `1`，`size` 默认 `20`，最大 `100`。
- 只返回当前景点的场次。
- 每条记录返回场次票种配置 ID、票种名称、实际售价、分配数量、剩余数量和销售状态。

## 获取场次详情

```http
GET /operator/sessions/{sessionId}
Authorization: Bearer <token>
```

用于查看场次或初始化编辑表单，返回场次基础资料和完整的票种配置。目标场次不存在或不属于当前景点时统一返回 `NOT_FOUND`。

## 新建场次

```http
POST /operator/sessions
Authorization: Bearer <token>
Content-Type: application/json
```

请求示例：

```json
{
  "visitDate": "2026-08-01",
  "startTime": "09:00:00",
  "endTime": "11:00:00",
  "bookingStartAt": "2026-07-20T09:00:00",
  "bookingEndAt": "2026-08-01T08:30:00",
  "totalCapacity": 500,
  "ticketTypes": [
    {
      "ticketTypeId": 1,
      "salePrice": 50.00,
      "allocatedQuantity": 350
    },
    {
      "ticketTypeId": 2,
      "salePrice": 30.00,
      "allocatedQuantity": 100
    }
  ]
}
```

业务规则：

- 新场次固定以 `DRAFT` 状态创建，不接受前端指定初始状态。
- 至少选择一个有效票种，`salePrice` 必须大于等于 `0`，`allocatedQuantity` 必须大于 `0`。
- 所有票种的 `allocatedQuantity` 之和不能超过 `totalCapacity`，超过时返回 `INVALID_REQUEST`。
- 后端写入当前登录运营者的 `venueId`。
- `remainingCapacity` 初始化为 `totalCapacity`。
- 每个票种的 `remainingQuantity` 初始化为对应的 `allocatedQuantity`。
- 场次与票种关联在同一事务内保存；任一票种不合法时整次创建失败。
- 同一景点存在完全相同的日期和时间段时返回 `CONFLICT`。
- 创建成功后返回新场次 ID。

## 修改场次

```http
PUT /operator/sessions/{sessionId}
Authorization: Bearer <token>
Content-Type: application/json
```

请求体与新建场次基本相同，不包含状态和剩余容量。

业务规则：

- 只能修改当前景点处于 `DRAFT` 状态的场次；已经开放、关闭、结束或取消的场次返回 `CONFLICT`。
- 可修改日期、时间、预约窗口、总容量、票种售价及票种分配数量。
- 因草稿场次尚未售票，修改总容量后将 `remainingCapacity` 同步为新的 `totalCapacity`。
- 修改草稿票种配置后，将各票种 `remainingQuantity` 同步为新的 `allocatedQuantity`。
- 修改后所有票种分配数量之和仍然不能超过新的 `totalCapacity`。
- 票种配置采用整组替换：删除原有 `session_ticket_type` 配置，再写入本次提交的配置，整个过程必须处于同一事务。
- 修改接口不能直接改变场次状态，状态变化使用独立的场次事件接口。

## 触发场次事件

```http
POST /operator/sessions/{sessionId}/events
Authorization: Bearer <token>
Content-Type: application/json
```

请求示例：

```json
{
  "event": "PUBLISH"
}
```

后端根据场次的当前状态和本次事件计算下一状态，前端不能直接指定目标状态。允许的状态转换如下：

| 当前状态 | 事件 | 下一状态 |
|---|---|---|
| `DRAFT` | `PUBLISH` | `OPEN` |
| `DRAFT` | `CANCEL` | `CANCELLED` |
| `OPEN` | `CLOSE_BOOKING` | `CLOSED` |
| `OPEN` | `CANCEL` | `CANCELLED` |
| `OPEN` | `SESSION_ENDED` | `ENDED` |
| `CLOSED` | `REOPEN_BOOKING` | `OPEN` |
| `CLOSED` | `CANCEL` | `CANCELLED` |
| `CLOSED` | `SESSION_ENDED` | `ENDED` |

附加规则：

- `PUBLISH` 和 `REOPEN_BOOKING` 执行前必须至少配置一个票种、存在可售数量、票种分配总量不超过场次容量，并且当前时间尚未超过 `bookingEndAt`。
- `CLOSE_BOOKING` 只停止新预约，不影响已有订单。
- `SESSION_ENDED` 只能在当前时间已经达到场次结束时间时执行；后台任务也只执行状态机允许的 `OPEN -> CLOSED`、`OPEN/CLOSED -> ENDED` 转换。
- 场次存在 `PENDING_PAYMENT`、`PAID` 或 `REFUNDING` 订单时不允许执行 `CANCEL`，以免产生未处理的库存、退款和票券问题；已取消、已关闭和已退款订单不阻止取消场次。
- `ENDED`、`CANCELLED` 为终态，不再接受任何状态事件。
- 当前状态不支持该事件，或事件前置条件不满足时，返回 `CONFLICT`。

## 删除场次

```http
DELETE /operator/sessions/{sessionId}
Authorization: Bearer <token>
```

业务规则：

- 只能删除当前景点的 `DRAFT` 场次。
- 存在任何订单记录的场次不能删除。
- 删除时先删除该场次的 `session_ticket_type`，再删除 `admission_session`，两步必须在同一事务中完成。
- 已开放、关闭、结束或取消的场次不做物理删除，应保留业务记录。

## MVP 范围

当前不提供批量创建、周期性排期、复制场次或开放后的配额调整。票种配额在草稿阶段由运营者确定，开放后保持不变。后台任务每分钟检查生命周期：预约截止后把 `OPEN` 场次关闭，参观结束后把 `OPEN` 或 `CLOSED` 场次收口为 `ENDED`。
